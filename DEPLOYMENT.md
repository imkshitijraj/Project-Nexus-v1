# Deploy Project Nexus

This guide covers publishing the source repository, deploying its static demonstration to GitHub Pages, and running the authenticated application with a separate Node/PostgreSQL service. Example domains, account names, and credentials below are placeholders; replace them with your own configuration.

## Choose a deployment

| Goal | What to deploy | Accounts and data |
| --- | --- | --- |
| Share a portfolio/demo website | GitHub Pages workflow | Personal browser-local workspace; no hosted login or shared database |
| Try the five login profiles on your laptop | `npm run start:demo` | Real local API permissions; sample accounts in a separate local database |
| Run a team application | Node service or Docker image plus PostgreSQL and SMTP | Real organization accounts and server-enforced permissions |
| Use Pages with hosted sign-in | Pages frontend plus the separately hosted API | Requires API configuration and compatible browser cookie policy |

Publishing source to GitHub does not start the API or publish a website automatically unless Pages and the deployment workflow have been enabled. GitHub Pages cannot run Node or PostgreSQL. For a commercial SaaS, use suitable application hosting and review [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).

## 1. Open and verify the local project

Open a PowerShell terminal in the project folder containing `package.json`. Install Node.js 24, then run:

```powershell
npm ci
npm run verify
```

For the login demonstration:

```powershell
npm run start:demo
```

Open `http://127.0.0.1:4174/`. The five profiles and local-only password are listed in [README.md](README.md#run-locally). These `.test` identities are not real mailboxes and are never provisioned during production startup. Stop the server with `Ctrl+C` before running browser tests on ports 4173/4174.

```powershell
npx playwright install chromium
npm run test:browser
```

Alternatively, set `$env:BROWSER_EXECUTABLE_PATH` to your installed Chrome executable. Review [VERIFICATION.md](VERIFICATION.md) for recorded checks and their limits.

## 2. Publish the repository with GitHub Desktop

1. Open GitHub Desktop and sign in to the account that should own this project.
2. Choose **File → Add local repository** and select this project's root folder. If Desktop says it is not a Git repository, use its **create a repository here** option, keeping the existing files in this folder. Do not create a second nested project directory.
3. Confirm the branch is `main`, because the supplied workflow deploys pushes to that branch.
4. Review the Changes list. Commit the source, documentation, `package-lock.json`, `.env.example`, and `.github/workflows/pages.yml`. Do not include actual `.env` files, database folders, access tokens, or private backups. `.gitignore` already excludes `.env*` except `.env.example`, `.data`, `node_modules`, `dist`, and test output.
5. If changes are uncommitted, create a commit such as `Prepare Project Nexus for deployment`.
6. Select **Publish repository**, choose the owner and repository name, review visibility, and publish. The repository URL shown by Desktop is the actual source URL; record it for future deployments. Availability of Pages for a private repository depends on your GitHub plan.

For an already published repository, use **Push origin**. If a remote is already configured, confirm it is the intended repository before pushing. Do not put credentials in a Git remote URL. GitHub Desktop handles account authentication.

## 3. Publish the static demonstration on GitHub Pages

1. On the repository website, open **Settings → Pages**.
2. Under **Build and deployment**, select **GitHub Actions** as the source.
3. Open **Actions → Verify and deploy Pages → Run workflow**, selecting `main`. Future pushes to `main` also trigger it.
4. Wait for both `verify` and `deploy` jobs to succeed. The workflow runs unit/API tests, dependency auditing, deployment tests, and all browser suites before uploading the public files.
5. Open the deployment URL shown in the successful job or Pages settings. For a project repository, its usual form is `https://OWNER.github.io/REPOSITORY/`; use GitHub's displayed URL as authoritative.
6. Enable **Enforce HTTPS** in Pages settings when available.

Leave the repository variable `NEXUS_API_URL` unset for the static demonstration. Only `dist/` is uploaded; it is generated by `npm run build:pages` from an explicit public-file allowlist. Source code, server files, databases, and secret environment files are excluded from the website artifact. Hash routes such as `#projects` work under repository subpaths.

After publication, check desktop and phone layouts, Light/Dark/System and accent settings, project creation, and persistence after reload. Static records belong to each browser and are not shared between people. A Pages account menu explains this rather than collecting a password.

## 4. Deploy the authenticated application

The simplest arrangement is one HTTPS origin: the Node service serves both the frontend and `/api`. Use an always-on Node host or a host supporting the included Dockerfile. Start with one API replica; current rate limits are process-local and schema startup must be coordinated before scaling.

Provision a PostgreSQL database and a real SMTP service first. Use a private database connection, provider-required TLS verification, and a database account limited to this application. Startup executes the supplied schema SQL, so that account needs the required schema creation/migration privileges. Do not disable certificate verification to fix a connection error.

Set these variables in the hosting provider's secret/configuration settings:

| Variable | Production value |
| --- | --- |
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `PORT` | Provider's assigned port, or `4174` |
| `DATABASE_URL` | Your PostgreSQL connection string, including provider-required TLS parameters |
| `JWT_SECRET` | Stable cryptographically random secret of at least 48 characters |
| `PUBLIC_URL` | Actual HTTPS frontend URL, e.g. `https://app.example.com` |
| `ALLOWED_ORIGINS` | Exact frontend origin, e.g. `https://app.example.com`; comma-separated if more than one, without spaces or paths |
| `SMTP_URL` | Your SMTP connection URL, e.g. `smtps://USER:PASSWORD@smtp.example.com:465` |
| `MAIL_FROM` | Verified sender, e.g. `Nexus <no-reply@example.com>` |
| `DEMO_SEED` | `0` |
| `TRUST_PROXY` | `1` only behind exactly one trusted reverse proxy; otherwise `0` |
| `CROSS_SITE_COOKIES` | `0` for the recommended same-origin/same-site deployment |

Generate `JWT_SECRET` locally with `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"` and transfer it to the host's secret store. Do not commit it, paste it into a browser-side file, or use the sample login password as a signing secret. Percent-encode special characters in URL credentials when required by your provider.

For a Node host, configure:

```text
Build command: npm ci --include=dev && npm run check && npm run typecheck
Start command: npm run start:server
Health path: /api/health
```

`tsx` is currently a development dependency used by the TypeScript start command. Keep development dependencies installed for this release; `npm ci --omit=dev` or a production install that omits them cannot start it. The Dockerfile already installs the required dependencies before setting `NODE_ENV=production`.

For Docker, build from this repository's root:

```powershell
docker build -t project-nexus:local .
```

Deploy that image through your host, inject the variables at runtime, route HTTPS traffic to port 4174, and set `/api/health` as the health check. Do not bake secrets into the image. On a self-managed server, terminate HTTPS at a correctly configured reverse proxy and expose the application only through that proxy. The image runs as the non-root `node` user. The live database resides in PostgreSQL, not in the container filesystem.

Once healthy, use **Create account** to create the first real organization administrator. Invite additional people from the administrator account, then add members/viewers to the projects they should access. Production has no pre-created demo administrator. Account registration is currently public; email ownership verification and MFA are listed as production release work in [SECURITY.md](SECURITY.md#production-release-gates).

## 5. Optional: connect a Pages frontend to the API

Deploy and verify the API first. In the GitHub repository, open **Settings → Secrets and variables → Actions → Variables** and create a repository variable named `NEXUS_API_URL` containing only its bare HTTPS origin, for example `https://api.example.com`. Do not use `/api`, a query string, credentials, or a secret. Re-run the Pages workflow so it rebuilds `runtime-config.js` and the frontend CSP.

On the API, set `PUBLIC_URL` to the frontend URL including the repository subpath, without a trailing slash, and set `ALLOWED_ORIGINS` to its origin only. For example, a frontend at `https://OWNER.github.io/REPOSITORY/` uses `https://OWNER.github.io/REPOSITORY` for account links and `https://OWNER.github.io` for the allowed origin.

An unrelated API domain and `github.io` frontend require `CROSS_SITE_COOKIES=1` in production; third-party-cookie blocking can still prevent refresh/login restoration. Prefer dedicated `app.example.com` and `api.example.com` domains under the same parent, or the single-origin deployment above. GitHub project repositories belonging to the same owner share an origin; do not combine a private application with untrusted applications on that origin.

To build the connected static files manually in PowerShell:

```powershell
$env:NEXUS_API_URL = 'https://api.example.com'
npm run build:pages
Remove-Item Env:NEXUS_API_URL
```

Upload only `dist/`. This command configures the frontend; it does not deploy an API or create accounts.

## 6. Verify the hosted release

Use a temporary test organization and accounts on the actual hosted URL. Check:

- `/api/health` responds with HTTP 200 and `{"status":"ok","version":1}`; HTTPS and redirects are correct.
- Registration, login, reload/session restoration, invitation email, reset email/link, account switching, and logout succeed. A reset invalidates the old sessions.
- A project/task persists across reload and service restart. Member and viewer restrictions match [API.md](API.md#permission-boundaries).
- Light/dark mode, narrow layouts, attachments, and PDF download work in the browsers you support.
- Production shows no demo profile picker, secret files are unavailable, and logs/monitoring capture failures without logging credentials.

Local tests do not establish production TLS, SMTP delivery, database restoration, load capacity, or compliance. Complete [SECURITY.md](SECURITY.md#production-release-gates) before accepting real organizational data. See [Operations and recovery](docs/OPERATIONS.md) for updates, backups, rollback, and troubleshooting.
